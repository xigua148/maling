## 0. 一句话背景

v1.5.2 已把底座夯实：角色系统（7 预设 + 自建 + 形象差分）、记忆系统（MemoryManager 偏好/话题/情绪）、亲密度（IntimacyTracker 4 级）、问候引擎（GreetingEngine 时段问候/Idle/纪念日）、主动陪伴（ProactiveScheduler 四重闸）、待办与知识库 GUI 入口（v1.5.0 空壳销项）。

用户拍板 v1.7 主攻**陪伴深化**——一句话概括：**她记得你说过的话（记忆本），她会带着内容来关心你（主动关心），她有每天的仪式感（时段问候/日记），她会准时叫你做事（贴身提醒），你们的关系会往前走（关系阶段/情绪陪伴），她的「人设」可以完全属于你（人设工坊），甚至可以呼朋唤友（多角色群聊 MVP）**。

基建已备，差最后一层体验：`build_topic_followup()` 已实现但从未接入主动问候；`page_memories.py` 现状是高光回忆册（HighlightsManager），MemoryManager 数据至今无 GUI 透出面；TodoManager 无时间字段，提醒从无触发链路。v1.7 就是把这层补上。

## 1. 增量范围

### 1.1 P0 第一梯队（4 项——基建已备差最后一层体验）

- **F1 女仆的记忆本 UI**：MemoryManager 数据透明化页面——主人偏好 / 活跃话题 / 情绪记录三类可视化，用户可查看 / 编辑 / 删除（信任感核心）。
- **F2 有内容的主动关心**：主动问候从纯模板升级为基于记忆——话题续接 + 情绪记录 + 待办状态三类内容源，生成有内容的关心（技术口径：规则为主，LLM 增强可选开关）；保持 A9 有节制频率红线。
- **F3 时段仪式感**：早安 / 午后 / 晚安分段仪式问候 + 每日一句（语录库为主、轻量 LLM 生成可选）；天气接入列为可选（无 API key 则整段跳过，不阻塞）。
- **F4 贴身提醒**：自然语言记日程（"周五下午3点提醒我开会" → 解析 → 到点系统通知）；解析口径 = 规则优先 + LLM 兜底；触发 = QTimer 调度器，与主动陪伴调度共存互不挤占。

### 1.2 P1 第二梯队（4 项——关系与情感深化）

- **F5 关系阶段叙事**：intimacy 4 级映射阶段叙事（初识→熟悉→亲近→信赖），每阶段解锁称呼 / 语气参数 / 小特权；阶段升级时女仆**主动告知一次**（一次事件）。
- **F6 情绪陪伴模式**：detect_emotion 检测到低落（tired / anxious / lonely）→ 进入安慰模式（system 注入情绪照顾指令 + 界面轻量视觉反馈）；情绪恢复后自动退出。
- **F7 女仆日记**：每日自动生成一篇日记（基于当日对话摘要，LLM 生成），存储为可翻阅的本地文件；入口放首页或记忆本页。
- **F8 人设工坊**：自建角色增强——①开场白设置 ②示例对话（few-shot）③角色卡导出 / 导入（JSON，可分享）。

### 1.3 P2 第三梯队（2 项——选定）

- **F9 人设工坊扩展**：**裁决 = 并入 F8 同批次交付**（见 §6.1 拆分口径），槽位保留作 F8 超裁时的顺延缓冲。
- **F10 多角色群聊（最小 MVP）**：用户选 2-3 个已建角色组成群聊会话；MVP 口径 = **用户@谁谁回** + 主动插话上限（防失控刷屏）。

### 1.4 明确不进 v1.7（Non-goals，用户拍板）

- **不做语音通话闭环**（TTS 朗读已有，双向实时语音对话不在本期）。
- **不做桌宠深化**（MaidPet 保持 v1.4.1 现状：默认关、可开，不加新互动形态）。
- **不做 AI 生成形象 / AI 生成角色立绘**（形象资产继续走本地 PNG 接入管线，不加文生图依赖）。
- 不做记忆 / 日记的云端同步与多设备（R-I 隐私红线的反面即边界）。
- 不做情绪历史的大数据分析 / 情绪报表 / 心情曲线图（R-A 无焦虑红线延伸：情绪记录只服务于"她此刻的照顾"，不做统计展示）。
- 不做群聊角色间的自由互辩 / 多轮接力（F10 MVP 边界，见 §6.2）。
- 不做提醒的跨设备推送 / 手机端联动（纯本机）。

## 4. P0 详细设计

### 4.1 F1 · 女仆的记忆本 UI

**用户故事**：作为主人，我想知道码铃到底"记住了我什么"——她记的偏好对不对、她在关心的话题是不是我还惦记的、她察觉到的情绪准不准；记错了我要能改，不想被记的我要能删。**记忆透明是我信任她的前提。**

**现状确认（代码核实）**：
- `memory.py MemoryManager` 已有完整读写接口：`list_preferences()` / `set_preference()` / `delete_preference()` / `get_active_topics()` / `forget_topic()` / `archive_stale_topics()` / `build_memory_context()`。
- **缺口一**：话题删除只有 `forget_topic`（软删除进 archived），无物理删除入口——记忆本需补"彻底删除"。
- **缺口二**：情绪记录现状只存单条 `habits.last_emotion / last_emotion_time`（memory.py:265-266），**无历史**——"情绪记录可视化"需增补 `emotions` 历史列表（增量字段，上限 50 条自动淘汰）。
- **缺口三**：`page_memories.py` 现状是**高光回忆册**（HighlightsManager 卡片流），与 MemoryManager 无关。记忆本需要**新页面**（建议 `gui/pages/page_memory_book.py`），不动回忆册。

**交互草案（文字描述）**：
- 侧栏新增「记忆本 📔」入口（置于「回忆 ✨」之下）；页面三个分区 Tab 或分节卡：**主人偏好 / 活跃话题 / 情绪记录**。
- **偏好区**：键值对卡片列表（如"nickname=小明"呈现为"称呼：小明"——内置常用键的友好名映射，未知键显示原名），每条右侧「✏️ 编辑」「🗑 删除」；顶部「➕ 添加偏好」手动录入（她想记住你告诉她的任何偏好）。
- **话题区**：活跃话题卡片（主题 + 最近提及时间 + 状态角标），操作「✔ 标记完成」「🗑 彻底删除」；底部折叠区"已归档话题"只读可展开。
- **情绪记录区**：时间倒序情绪条目（时间 + 情绪标签 + 当日触发消息摘要 ≤30 字），每条可删；**顶部一行中性说明**："码铃从你的话里察觉到的情绪，只用来在当下更好地陪你，绝不做统计。"（R-A / R-I 双合规文案）
- 页面底部固定一行：「📔 这里的一切只存于你的电脑，删除立即生效。」
- **红线自检**：无条目计数徽章、无"记忆容量已用 N%"、无任何进度语义。

**数据 / 接口依赖**：
- `memory.py`：增补 `emotions` 历史列表（结构 `{time, emotion, excerpt}`，append 时淘汰 >50 条）、`delete_topic_forever(subject)`、`set_preference` 已够用；`build_memory_context()` 注入逻辑不变（仍读 preferences + active topics）。
- GUI：新 `page_memory_book.py`，注册进 Sidebar / PageManager；取色一律 `theme_color`，禁裸色。

**验收标准**：
1. 三分区数据与 `~/.maid_coder/user_memory.json` 实时一致；任何增删改后立即落盘（原子写）。
2. 删除偏好 / 话题后，**当轮起**`build_memory_context()` 不再包含该条目（删除即遗忘，可自动化断言）。
3. 情绪记录上限 50 条自动淘汰；无历史数据时分区显示中性空态（"还没记住什么，慢慢来~"）。
4. 全页 theme_color 取色，深色模式无裸色残留；红线扫描词（§2 R-A 扩展词表）零命中。
5. 旧版 user_memory.json（无 emotions 字段）加载不崩，`_merge_defaults` 自动补全。

**风险与工作量**：低风险。1.5–2 人日（memory.py 增量 0.5d + 页面 1–1.5d）。**优先级理由**：P0 之首——记忆系统跑了一年但用户"看不见摸不着"，透明化是本期"信任感"叙事的地基；且 F2/F7 均以记忆数据为原料，UI 先行便于联调观察。

### 4.2 F2 · 有内容的主动关心

**用户故事**：作为主人，我不想收到"在吗~"这种空招呼——我希望她开口时带着"上次你提到的「考研报名」有进展了吗"这样记得我的内容；如果她只是干巴巴地问好，我宁愿她安静待着。

**现状确认（代码核实）**：
- `memory.py build_topic_followup(min_hours, max_hours)` **已完整实现**（返回"上次主人提到的「X」，现在有进展了吗？"），但**全树无调用方**——这是典型"有实现没接线"。
- `greeting.py GreetingEngine.generate_greeting(nickname, intimacy_level, memory_topic)` 有 memory_topic 参数但只做字符串拼接，且该参数在 GUI 接线处从未传过实质内容。
- `gui/proactive_scheduler.py` 三类触发场景白名单（agent_revisit / low_emotion / idle_hello）+ 四重闸 + 防自续命，机制健康。
- `TodoManager.items()`（v1.5.0）可读待办列表——但本期 F4 才给条目加时间字段，F2 的待办维度先用"未完成待办条数"轻量接入。

**技术口径裁决（PM 定）**：**规则拼装为主，LLM 增强为可选开关**。
- 理由：主动问候是高频低值场景，LLM 逐次生成 = token 成本 + 3–10s 延迟 + 失败处理复杂度，且 A9 场景里"温柔的一句话"模板已够温度；复用 `agent.proactive.llm_enhance` 既有配置位（默认 false，与 v1.2 口径一致），开了才走 LLM 润色。
- **内容拼装优先级**（同次问候最多带 1 条内容，宁缺毋滥）：①话题续接（`build_topic_followup(1, 72)` 命中 → 最有"她记得你"的分量）②情绪延续（上次情绪为 tired/anxious/lonely 且在 24h 内 → "昨天感觉你有点累，今天好些了吗"）③待办轻提（未完成待办 ≥1 且 ≥24h 未动 → "便签上还留着一件没做完的事，需要我帮你理理吗"——**不点名具体内容**，避免变成催办焦虑）。

**交互草案（文字描述）**：
- 触发点沿用 A9 既有场景，不新增触发类型：idle_hello（长空闲问候）与**每日首次打开的启动问候**（gui/main.py 既有接线）两处挂内容拼装。

### 5.2 F6 · 情绪陪伴模式

**用户故事**：作为主人，当我加班到崩溃或焦虑到睡不着时，我不想再收到技术问题反问——我希望她能察觉到，把语气放缓，安安静静陪着我，等我缓过来一切照旧。

**现状确认（代码核实）**：

- `companion.py MoodState.owner_emotion` 已存最近情绪；`proactive_scheduler.py` 的 low_emotion 场景已用 NEGATIVE_EMOTIONS = (tired, anxious, lonely) 做"近 5 分钟"关心——**但只触发一条主动问候，不改变此后对话的语气**。
- **缺口**：无"模式"概念——低落检测后单轮关心即结束，后续对话仍按日常人设节奏（可能继续提技术问题、给任务式建议）。

**交互草案（文字描述）**：
- **进入**：detect_emotion 命中 tired / anxious / lonely → 连续 2 轮内（或单轮强信号，如"好累好想哭"级关键词命中）进入**安慰模式**：①system 注入情绪照顾指令块（"主人现在状态不好：语气放缓放轻、多用陪伴式回应、不主动提技术问题、不给任务式建议、先接住情绪再谈事、可以适当多用动作描写传递温度"——具体措辞架构定稿）；②界面轻量反馈：聊天面板出现一枚柔和状态徽标（如"🌙 陪伴中"小 chip，点开一句话说明"码铃注意到主人有些低落，会放缓节奏陪着你，随时可以让我恢复正常"）；头像表情差分切 concerned 系（38 图资产已有，零新增）。
- **退出**：①用户明说（"我好了/没事了/恢复吧"或徽标上点"恢复正常"）→ 立即退出；②自动退出：此后连续 N 轮（默认 4）未再命中负面情绪关键词 → 自动退出 + 徽标轻淡出；③系统注入仅持续安慰模式期间，**不写入会话历史**（退出后 LLM 历史无残留指令——每轮动态注入，非一次性消息）。
- **红线自检**：不问"你抑郁吗"式诊断话术、不推荐心理咨询链接（越界关怀比不关怀更伤人）、无情绪分数展示（R-A）；徽标永远可一键关闭（尊重用户不想被"特殊对待"的心情）。

**数据 / 接口依赖**：
- `gui/chat_service.py`：system 组装链增量——安慰模式开时在 system 尾部注入指令块（每轮重建，与 build_memory_context / intimacy prompt 同位置同模式）；模式状态机（entering/exiting 计数）放 `companion.py` 或独立 `care_mode.py`（架构裁决，建议 companion 内轻量实现）。
- `memory.py detect_emotion`：零改动（现规则够用；词库可选扩充几个高强度词）。
- `gui/widgets/chat_panel.py`：状态 chip + 恢复按钮（theme_color 取色）。
- 表情差分：`expr_markup.py` 既有管线，仅映射 concerned/sad 系表情。

**验收标准**：
1. 命中低落 → 当轮回复语气可感知放缓（LLM 评测抽样 + QA 人工 5 用例）；system 含照顾指令且**不含**于会话持久化历史。
2. 连续 4 轮无负面关键词 → 自动退出；手动恢复立即生效；徽标显隐与模式状态一致。
3. happy/normal 轮次永不误入模式（反向用例）。
4. 模式期间主动陪伴 low_emotion 场景零回归（不重复关心）。
5. 徽标可关闭且关闭不影响模式运作（仅视觉）。

**风险与工作量**：**中风险**（"安慰语气"效果依赖模型水平，弱模型可能注入无效——验收口径需包含弱模型降级预期）。1–1.5 人日。**优先级理由**：P1——低落时刻的陪伴质量是情感深化的核心场景，且全是增量注入、不碰既有链路。

### 5.3 F7 · 女仆日记

**用户故事**：作为主人，我想在某个周末午后翻看"她眼中的我们"——她今天记下了我说过的哪句话、我们聊了什么、她自己的小心情。日记是她视角的、带着她人设温度的，不是冷冰冰的聊天记录导出。

**现状确认（代码核实）**：
- 无任何日记基建；但生成原料充足：ChatService 会话历史 + MemoryManager 偏好/话题 + companion 心情；LLM 生成链（OpenAI 兼容 API）成熟。
- 高光回忆册（highlights.py）提供了"本地 JSON + 原子写 + 上限淘汰"的存储范式可参照。

**交互草案（文字描述）**：
- **生成时机（默认口径）**：**当日首次启动时补写昨日日记**（若昨日有对话且未写过）——好处：对话已完整、不打断当天使用、失败可次日重试。备选口径"当日退出时生成"（会话更完整但用户关机跳过风险高）——**列入 Q-C6 请用户拍板**。
- **生成方式**：LLM 单次调用：提示词 = "以 {角色名} 的第一人称写一篇 100–200 字的日记" + 当日对话**摘要要点**（MemoryManager 提取的偏好/话题变化 + 高光回忆当日新增条目 + 情绪记录 + 当日消息数）——**不发送完整原始对话**（R-I 硬线：控制 token 成本 + 隐私外发最小化）。生成以该角色人设口吻落笔（不同角色日记风格不同）。
- **翻阅 UI**：新页或记忆本页内 Tab「她的日记」：按月分组的时间倒序列表 → 点开单篇日记卡（日期 + 心情小表情 + 正文）；支持「导出为 Markdown」（单篇 / 全部打包）到用户自选目录。
- **存储**：`~/.maid_coder/diaries.json`（或 diaries/ 目录逐年 JSON——架构裁决，条目量小建议单文件 + 上限 365 篇滚动淘汰）。
- **红线自检**：无"连续写日记 N 天"打卡语义；日记生成失败静默（次日重试），**绝不生成占位假日记**（码铃产品"诚实"底线：宁可缺一天不可编造）；生成消耗在首页 Token 卡自然累计（不单独提示焦虑）。
- **开关**：设置页「陪伴」区「女仆日记」开关（默认**开**——日记是本期核心体验；但 LLM 不可用/无 key 时自动停用并留一次性说明）。

**数据 / 接口依赖**：
- 新 `diary.py`（根级纯 stdlib 存储 + 生成提示词组装）：`ensure_yesterday_diary(session_history, memory_mgr, highlights, companion, persona)`。
- `gui/main.py`：启动挂载生成检查点（工作线程，不阻塞启动）。
- `page_memory_book.py`（F1 新页）：内嵌「她的日记」Tab；或独立页（架构裁决，建议并页省侧栏位）。
- 导出：纯 stdlib 文本拼接写 Markdown。

**验收标准**：
1. 昨日有对话 + 未写过 → 今日启动 5 分钟内日记可翻阅；生成内容含角色口吻与当日要点（抽样人工评审）。
2. R-I 断言：生成请求 payload 不含完整对话原文（仅摘要要点，自动化断言 payload 长度/内容）。
3. 无 LLM / 生成失败 → 静默跳过不落占位文；次日重试成功。
4. 导出 Markdown 中文无乱码；翻阅页 theme_color 合规、深色模式正常。
5. 开关关闭 = 零生成零 token；上限淘汰生效（>365 篇丢最旧）。

**风险与工作量**：**中风险**（token 成本感知 + 生成质量依赖模型）。1.5–2 人日。**优先级理由**：P1——"她眼中的我们"是本期情感叙事的高光交付；与 F1 记忆本并页开发，数据链共享。

### 5.4 F8 · 人设工坊

**用户故事**：作为主人，我想让"我的码铃"真正是我的——新会话她第一句就说我们约定好的话；给她几组我们的对话示例，让她学会我喜欢的相处方式；还能把这份人设导出来分享给朋友、或把朋友的角色卡导入进来。

**现状确认（代码核实）**：
- 角色系统成熟：page_role.py 7 预设 + 自建 + 性格滑块真注入 + 头像自定义 + v1.5.2 提示词编辑弹窗；角色 JSON 持久化稳定。
- **缺口**：①无开场白机制（新会话首条 assistant 消息是固定欢迎语）；②无 few-shot 示例对话；③无导入导出（角色绑定本机）。
- v1.5.1 已修"切角色人设残留"（角色切换边界 system 消息 + 会话↔LLM 历史对齐）——F8 开场白须**复用该对齐机制**，避免新会话首条与 LLM 历史分叉。

**交互草案（文字描述）**：
- **①开场白**：角色编辑面板新增「开场白」多行输入（留空 = 既有默认欢迎语）；新会话 / 切换到该角色的新会话时，首条 assistant 气泡显示开场白（带表情标记支持，走 expr_markup 既有解析）；开场白**入 LLM 历史**（作为 assistant 首条），使后续对话自然衔接。
- **②示例对话**：角色编辑面板新增「示例对话」编辑区（最多 5 组，每组 = user 一句 + assistant 一句，多行文本或简易双列编辑）；注入方式 = system 尾部追加"【对话风格示例】"块（few-shot 塞 system 而非 messages——**不占历史轮次、不影响历史对齐机制、token 可控**，与既有 build_intimacy_prompt 注入同模式）。
- **③导出/导入**：角色卡右键 / 编辑面板「📤 导出角色卡」→ 保存 `.malingcard.json`（含：名称、系统提示词、性格三值、开场白、示例对话、表情偏好元数据；**不含**头像图片本体路径、记忆、亲密度、对话历史——R-I）；「📥 导入角色卡」→ 文件选择 + 校验 + 冲突处理（重名 → 自动加后缀"（导入）"，绝不覆盖既有角色）；导入成功气泡提示 + 角色列表即时可见。
- 预设角色（7 套）同样可导出（分享入门人设），但导出前弹提示"这是预设角色的副本"。

**数据 / 接口依赖**：
- 角色 JSON schema 增补 `greeting_message` / `example_dialogues` 字段（向后兼容：旧卡缺字段 = 默认值）。
- `gui/chat_service.py`：新会话 / 切角色链路注入开场白（复用 v1.5.1 历史对齐重建点）；system 组装链追加示例对话块。
- `page_role.py`：编辑面板两块新输入 + 导入导出按钮 + JSON 校验器（拒绝超限字段、体积上限 1MB）。
- 表情标记：开场白经 `expr_markup.py` 既有解析渲染。

**验收标准**：
1. 设置开场白的新角色：新会话首条 assistant 消息 = 开场白原文（含表情标记渲染）；旧角色无开场白 = 默认欢迎语零回归。
2. 示例对话注入后，回复风格向示例偏移（QA 5 用例人工评审）；注入块不进会话历史、不随消息气泡显示。
3. 导出 → 删除本机角色 → 导入同卡：角色完整还原（字段逐项断言）；导入文件含异常字段/超限时被拒并有明确提示。
4. 切角色 / 新建会话 / 重启后开场白与示例对话稳定生效；v1.5.1 人设残留修复零回归。
5. 旧角色 JSON 加载不崩；schema 迁移零操作。

**风险与工作量**：**中风险**（v1.5.1 历史对齐链是敏感区，开场白注入点需谨慎）。2–2.5 人日。**优先级理由**：P1——"我的码铃"是从"用产品"到"养伙伴"的跃迁点；导入导出让角色生态可流通，社区价值高。

### 6.2 F10 · 多角色群聊（最小 MVP）

**用户故事**：作为主人，我想把我建好的两三个角色拉进一个房间——我 @ 谁谁就答，偶尔她们自己搭句话，像有个小小的客厅。热闹，但不失控。

**技术复杂度标注（如实）**：**全池最高**。群聊打破"单角色 system 唯一"的既有会话模型（v1.5.1 刚把"人设来源唯一"收口）；每次发言 = 一次独立 LLM 调用（各自 system + 共享群聊历史 + 各自头像渲染）；发言调度、历史对齐、亲密度隔离、token 成本翻倍四座大山。**因此 MVP 边界必须收得很紧**。

**MVP 口径（PM 建议，待 Q-C1 拍板）**：
- **组建**：聊天侧新建「群聊会话」→ 从已建角色中选 2–3 个 → 群聊会话与普通会话同列表管理（标签区分）。
- **发言调度 = 用户 @ 指定（首版唯一策略）**：输入"@角色名 内容"（输入框 @ 补全）→ 被指定角色以其人设回复一次；无 @ 前缀的普通消息 → **默认轮转第一位**（可设置改为"全部沉默等待 @"）。轮转顺序用户可拖换。
- **主动插话上限**：设置开关（**默认关**）；开启后每条用户消息后最多 1 个未指定角色主动搭话、全局冷却 ≥3 分钟、每日群聊插话上限 5 次——四道闸防刷屏失控（R-J）。
- **渲染**：各角色发言用各自头像 + 各自名字气泡；共享同一条群聊历史（单文件存储，会话 JSON 标 type=group + members 列表）。
- **明确不做**：角色间自由互辩、多轮接力、群聊内表情联动规则、群聊亲密度计分（R-J⑤）、群聊 TTS 多声线。这些是 v1.7+ 演进空间。

**数据 / 接口依赖**：
- ChatService 会话层：群聊会话类型 + 按成员切换 system 的发言循环（发言 = 独立 API 调用，串行防并发错乱）。
- 会话存储 schema：type/members/turn_order 字段（旧会话零影响）。
- 聊天面板：@ 补全、群成员头像渲染、群会话标签角标。
- 角色系统：零改动（群聊只读角色卡）。

**验收标准**：
1. 2–3 角色群聊：@A 则仅 A 回复（人设/头像正确）；无 @ 时按既定策略（轮转或沉默）。
2. 插话默认关；开启后单条消息插话 ≤1、冷却/日上限生效（自动化断言四道闸）。
3. 群聊会话与普通会话互不串人设（v1.5.1 回归全绿）；群聊不计亲密度。
4. 群聊历史持久化 / 重启恢复 / 删除会话干净。
5. 单轮 token 消耗在首页 Token 卡如实累计。

**风险与工作量**：**高风险**（会话模型变更 + token 成本 ×N + 调度边界多）。3–5 人日。**优先级理由**：P2——用户明确点名要（"呼朋唤友"的乐趣），但复杂度与 P0/P1 不在一个量级；放 P2 末位、裁剪优先级最高（资源紧张时第一个砍，且砍掉不影响本期主题完整性）。

## 7. 与既有红线映射 / 澄清（防团队误读）

| 问法 | 澄清 |
|---|---|
| 「F5 阶段升级播报是不是变相做养成系统？」 | 不是。升级播报是**一次性的关系叙事事件**（v1.2 就有的 _check_level_up 文案升级为主动播报），播报本身无数值、不展示进度、不制造"再聊几句就升级"的预期——用户无从知道分数阈值（阈值永不入 UI）。R-A 的禁令对象是"数值可见性"，不是"关系在变化"这一事实本身。 |
| 「F1 记忆本把偏好摊出来，会不会变成用户去'优化记忆'的刷分行为？」 | 记忆本是**透明与纠错工具**，不是养成面板：无条目数目标、无容量语义、无任何"记忆越多越好"暗示文案；删除与编辑是平等的一级操作。 |
| 「F4 提醒用系统弹窗，违反 R-C 不打扰推送吗？」 | 不违反。R-C 判例（v1.4 番茄钟）已确认：**用户主动设置的定时提醒 = 用户预期动作**。且本项仍做了三重克制：quiet 免打扰时段静默顺延、同条提醒只通知一次、确认卡 5 分钟可撤销。与"码铃主动推送营销式内容"有本质区别。 |
| 「F6 情绪模式算不算监督用户情绪？」 | 不算。detect_emotion 只分析**用户自己主动打出来的文字**（既有 v1.2 机制，非新增采集），不感知摄像头/麦克风/在场（R-B 永不做）；模式效果是"她自己的语气变化"，不给用户任何"你被监测"的展示（无情绪历史图表——Non-goals 明确排除）。 |
| 「F7 日记发给 LLM 生成，会不会把我的对话传出去？」 | R-I 硬线：生成请求只含**摘要要点**（话题名 / 情绪标签 / 高光条目 / 消息数），不含完整对话原文；所有日记存储在本地。这与普通聊天本身会把消息发给 API 是同一隐私水位（用户已知情同意的模型调用），但日记做了最小化收敛。 |
| 「F10 群聊多个角色会不会互相'串人设'？」 | v1.5.1 已把"人设来源唯一"收口。群聊的每次发言都是独立 LLM 调用（各自 system 头），共享的只有群聊历史文本——历史中他人的发言对当前角色只是"上下文中看到的别人说的话"，属正常多轮对话语义，不污染 system。验收标准 3 专项覆盖。 |
