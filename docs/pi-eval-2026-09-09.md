## 结论先行

**建议：有条件接入（薄适配层 + 授权门禁扩展），作为码铃"编程模式"的可选执行引擎试点；暂缓全面替换内置 AgentEngine。**

Pi 宣称的核心能力（多模型接入 / 工具调用 / 流式事件 / 停止中断 / 会话树 / 上下文压缩 / 项目指令 / 技能扩展 / RPC 模式）**在 Windows 11 + Node 22 + DeepSeek 环境下全部实测存在且可用**，无一虚假宣传。同时实测发现码铃内置引擎在纯编程任务上 token 消耗约为 Pi 的 1.5～5 倍、轮数更多，主要开销在系统提示词 + 15 个工具 schema 的每轮全量携带，以及严格白名单带来的拒绝-重试循环。

## 第二步：RPC 模式实测（Python subprocess ↔ pi --mode rpc）

启动方式：`pi --mode rpc --no-session --provider deepseek --model deepseek-v4-flash`（Windows 下为 `pi.cmd`，subprocess 需全路径）。

### ① 纯对话 ✅
```
→ {"id":"t1","type":"prompt","message":"用一句话回答：1+1等于几？"}
← {"id":"t1","type":"response","command":"prompt","success":true}
← {"type":"agent_start"} ... text_delta 事件流 ... {"type":"agent_settled"}
```
耗时 1.63s，回答正确。

### ② 工具调用 ✅
```
← {"type":"tool_execution_start","toolCallId":"call_00_r26BHCYl5EhHyXsfUKD42745","toolName":"read","args":{"path":"hello.txt"}}
← {"type":"tool_execution_end","toolCallId":"call_00_...","toolName":"read","result":{"content":[{"type":"text","text":"码铃 Pi 评测：HELLO_FROM_MALING_20260909"}]},"isError":false}
```
模型正确调用 `read` 工具并复述文件内容，`isError: false`。

### ③ 流式逐块到达 ✅（真实流式，非一次性返回）
"从 1 数到 30"任务产生 **59 个 text_delta 事件**，平均到达间隔 **4.3ms**，最大间隔 51ms：
```
3.178s → "1"   3.198s → "\n"   3.198s → "2"   3.198s → "3" ...
```

### ④ 停止（中断）✅
长文生成中途发送 `{"type":"abort"}`，2.75s 内收到 `agent_settled`，最终 assistant 消息 `stopReason: "aborted"`。

### 附加：RPC 管理面 ✅
`get_state` / `get_session_stats`（返回分项 token/cost/contextWindow 百分比）/ `get_tree`（实测返回 6 节点会话树 + leafId）均正常。`compact` 在小会话上正确返回守卫错误 `"Nothing to compact (session too small)"`（端点存在、守卫逻辑正确；**满负荷压缩效果因成本考虑未做大数据量实测**，官方文档描述为摘要式有损压缩、自动触发可配置）。

### JSONL 帧协议注意事项（实测确认）
- 严格 LF 分帧；文档明确警告不要用 Node `readline`（U+2028/U+2029 会误切分）。Python `readline` 实测无恙。
- 事件即行即发，subprocess 管道无缓冲卡顿。

## 第三步：真实任务对比（同一模型 deepseek-v4-flash）

任务均在独立快照目录冷启动；码铃走源码态 `AgentEngine.run()`（agent_engine.py + agent_tools，workspace 白名单自动放行、confirm_fn=None）；Pi 走 RPC 无门禁（无--session）。结果正确性均为**人工/脚本复验**，不采信模型自述。

| 任务 | 引擎 | 完成与复验 | 耗时 | LLM 轮数 | token（全口径） | 拒绝/误操作 |
|---|---|---|---|---|---|---|
| A: CSV 解析统计脚本 | 码铃 | ✅ 输出复验正确 | 12.1s | 5 | 17,137 | 0 |
| A | Pi | ✅ 输出复验正确 | 8.7s | 5 | 11,711 | 0 |
| B: 修复 Kadane 全负数组 bug | 码铃 | ✅ 三用例 6/1/-1 复验通过 | 50.9s | 11 | 61,030 | 2 次拒绝（shell 元字符 `;`、run_python 未授权） |
| B | Pi | ✅ 三用例 6/1/-1 复验通过 | 13.3s | 4 | 11,550 | 0 |
| C: pytest 单元测试 | 码铃 | ✅ 复验 25 passed | 23.0s | 5 | 21,275 | 1 次拒绝（`pytest -v` 不在命令白名单，模型自行降级重试成功） |
| C | Pi | ✅ 复验 35 passed | 16.4s | 4 | 14,803 | 0 |

> token 口径说明：码铃取 DeepSeek 流式末帧 `prompt_tokens+completion_tokens` 累计；Pi 的 usage 将 cacheRead 单列（首轮输入大量计入 cacheRead），上表为 input+output+cacheRead+cacheWrite 全口径。两端口径已对齐，但实现层计费细节可能有细微出入，量级结论不受影响。

**要点解读：**
1. **正确性打平**：三个任务双方都完成且复验通过，deepseek-v4-flash 在两套脚手架下表现一致，引擎层不构成能力瓶颈。
2. **效率 Pi 占优**：Pi 平均省 30%～80% token、轮数更少（B 任务 4 轮 vs 11 轮）。主因：码铃每轮全量携带系统提示 + 15 个工具 schema（B 任务 11 轮 × ~5k input），且 run_command 白名单拒绝后模型需要额外轮次自纠。
3. **码铃白名单的摩擦是双刃剑**：实测拒绝了 `ls`、含 `;` 的复合命令、`pytest -v`（安全上完全正确、fail-safe），代价是 B 任务多烧约 5 万 token。这些正是设计取舍（design-v12 D3 定稿常量集），不是 bug。
4. **实验中踩到的真实坑**：码铃工具授权按进程 cwd 解析相对路径——驱动进程 cwd 与 workspace 不一致时，模型写的 `taskA/analyze.py` 被判越界拒绝（fail-safe 正确，但 headless 集成时必须保证 cwd=workspace，GUI 运行态天然一致；连续两次跑挂即此原因，修正后 12s 通过）。**若接 Pi，Pi 的 cwd 即工作区，无此歧义。**

## 第四步：接入可行性评估

### ① RPC confirm/select/input 交互事件是否真实存在且能映射码铃授权弹窗？——✅ 实测通过
Pi 本体"无权限弹窗"（philosophy），但提供扩展 UI 子协议。实测自写 20 行门禁扩展（`tool_call` 事件 → `ctx.ui.confirm`）+ Python RPC 客户端全链路：

```
← {"type":"extension_ui_request","id":"4707f784-...","method":"confirm","title":"码铃授权确认","message":"Agent 请求执行工具 [bash]，是否允许？"}
→ {"type":"extension_ui_response","id":"4707f784-...","confirmed":false}   # 拒绝 → 工具被 block，模型收到拒绝原因
→ {"type":"extension_ui_response","id":"...","confirmed":true}             # 允许 → bash 执行成功
```
拒绝场景工具确实未执行、模型如实向用户报告"被拒绝"。**与码铃 `AgentTools.authorize()` 的 confirm_fn 弹窗语义一一对应**，`timeout` 字段还支持超时自动裁决（可映射码铃的静默默认拒绝策略）。

### ② 工作区限制/权限机制能否覆盖码铃授权白名单需求？——✅ 可覆盖，但需自带扩展
Pi 无内置工作区沙箱（官方立场：容器化或扩展自建）。实测路径：`--tools read,grep,find,ls` 可裁剪为只读；写类操作用 `tool_call` 扩展事件拦截（`{block:true, reason}` 已实测生效），在扩展内复用码铃白名单逻辑（workspace 路径判定 + 命令黑名单）即可。迁移成本约 60～100 行 TS。**注意**：这是"应用层约定"而非引擎强制，码铃需在适配层固定加载该门禁扩展，防止漏载。

### ③ 上下文压缩/会话树是否实测可用？——✅ 协议层可用（压缩效果未满负荷实测）
`get_tree` 实测返回带 children 的会话树 + leafId（ branching 会话为单文件 JSONL 树结构）；`compact`/`set_auto_compaction` 端点实测可达，小会话正确拒绝压缩（守卫正确）。自动压缩（overflow 恢复 + threshold 预压）为文档声明 + 代码可见，未做长会话满负荷实测（成本考虑，诚实记录）。

### ④ Windows 兼容性坑——✅ 总体干净，坑均可绕
- 可执行文件是 `pi.cmd` shim：subprocess 需全路径或 shell 解析（已实测绕过）。
- bash 工具在 Windows 实测可用（任务 A/B/C 的命令执行都经它完成），另有 powershell 工具可选。
- GitHub 直连不稳定，克隆需走镜像；npm 安装本身正常。
- JSONL 严格 LF 分帧，Windows 文本模式 `text=True` 实测无 `\r` 问题（协议支持容忍 `\r\n`）。
- 未遇到编码/路径分隔符类问题。

### ⑤ 薄适配层规模估算（码铃侧，Python 为主）

| 模块 | 内容 | 规模 |

## 风险与未尽事项（诚实记录）

1. compact 满负荷效果未实测（小会话守卫已验证）；若码铃长对话场景依赖压缩，接入前应补一次长会话实测。
2. Pi 无内置权限强制：门禁依赖扩展常载，部署脚本需把 `-e maling_gate` 写死并回归验证；否则 bash 工具默认全开。
3. Pi 迭代快（0.85.x），RPC 协议文档完善但非 LTS 承诺；适配层应锁定版本。
4. 码铃 `run()` 的 managed 任务体系（C3 规划/C2 自愈/断点暂停）在 Pi 侧无对应物——Pi 走"一次 prompt 到 agent_settled"模型；若要保留码铃任务管理，需由码铃侧编排多次 RPC 调用，或维持双引擎并存。
5. 本对比为单模型（deepseek-v4-flash）× 3 任务的小样本，效率结论方向可信，精确倍数不宜外推。

## 建议

1. **接入**：以 RPC 子进程 + 门禁扩展方式接 Pi，作为"编程模式"执行引擎试点（新功能，不动存量聊天/陪伴路径）。
2. **并存**：码铃 AgentEngine 保留处理轻量工具对话与 managed 任务；Pi 承担纯编程任务（实测效率优势 30%～80% token）。
3. **白名单复用**：把码铃 workspace 白名单/命令黑名单逻辑移植进门禁扩展（而非依赖 Pi 内置），保持两端授权语义一致。
4. 若后续长会话压缩实测不达标或 Pi 协议破坏性变更频繁，退回"仅内置引擎"的成本极低（适配层为独立模块）。
